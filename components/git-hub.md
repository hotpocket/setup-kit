# git-hub — a machine that holds bare repos its workers push to

**Status:** opt-in (`component_git_hub=yes` on the hub; `git_hub=<host>` on a worker).
Code: `components/git-hub/` (lib, hook, `git-hub` CLI); hub side in
`profiles/workstation/07-components.sh`, worker side in `profiles/worker/03-headless.sh` §8.
Calibration: `tests/test-git-hub.sh`.

## Why

A worker (ai-3090) commits to repos outside its domain — the PAT that pushes its
own line is scoped, so those commits sat on the box awaiting a "fetch request".
Widening the PAT gives an unattended LLM-driven box write access to GitHub. Instead
the worker pushes to a **hub**: bare repos on a machine the human controls. What
leaves the hub for GitHub, and what gets deployed, is the human's act.

```
worker ──ssh, git-shell only──▶ hub:/srv/git/<name>.git ──human: git-hub forward──▶ GitHub
                                        │
                                        └──human: git-hub stage <name>, then the deploy command it prints
```

## The one knob

On the worker: **`git_hub=<host>`** — the hub's address. Nothing else names it.

- Every hub-routed clone's `origin` is `git-hub:<name>.git`. `git-hub` is an ssh
  alias; its `HostName` is the only place the address lands (a managed block in
  `~/.ssh/config`, reconciled by content).
- Moving the hub is: stand the new hub up (same `git_hub_repos`, same pushers file),
  seed it (`git push --mirror` from the old one), change `git_hub=` on each worker,
  re-run `worker install`. No remote URL changes, nothing in any repo changes.
- Empty/unset = off; the worker's remotes are left alone.

## Knobs

Both sides list their repos the way `clone_repos` does: `owner/repo[:path]`. The
bare repo is `<basename>.git`; `owner/repo` is its GitHub upstream; `:path` is where
*this host's* working clone lives under `$GIT_HOME` (default: the basename).

| key | side | meaning |
|---|---|---|
| `git_hub` | worker | hub address (IP or name). The move-the-hub knob. |
| `git_hub_repos` | both | worker: which clones route via the hub. hub: which bare repos exist. |
| `component_git_hub` | hub | `yes` provisions the hub. |
| `git_hub_root` | hub | default `/srv/git` (the `git` user's home). |
| `git_hub_pushers` | hub | file of public keys allowed to push, one per line; the kit renders them into the `git` user's `authorized_keys`, each prefixed `restrict`. |
| `git_hub_deploy` | hub | `name=command ...` — what `git-hub stage <name>` tells the human to run. Printed, never run. |

## Authentication: worker → hub

- Worker: its own ed25519 key `~/.ssh/git_hub` (generated by install, no passphrase,
  no agent, `IdentitiesOnly`). No YubiKey — a cron can't touch one.
- Hub: a dedicated system user `git`, login shell `/usr/bin/git-shell`, home
  `git_hub_root`. git-shell runs only `git-receive-pack` / `git-upload-pack` /
  `git-upload-archive`; there is no `git-shell-commands`, so no interactive login.
  Keys carry `restrict` (no pty, no forwarding). `~/.ssh` and `authorized_keys` are
  root-owned so a push can never rewrite who may push.
- The worker can therefore read and fast-forward the hub's repos and nothing else on
  the hub. Every bare repo has `receive.denyNonFastForwards`, `receive.denyDeletes`,
  `receive.fsckObjects`: an agent can add history, never rewrite or remove it.
- Host key: `StrictHostKeyChecking accept-new` (first use on the LAN). A moved hub is
  a new host entry, not a mismatch, because the alias does not set `HostKeyAlias`.

## Hub side

- Bare repos are created **empty**; the first push from the worker seeds them with
  its full history (workers are usually ahead of GitHub — that is the point).
- `post-receive` (one copy under `<root>/.hooks`, `core.hooksPath`) appends one JSON
  line per ref to `<root>/log/receive.jsonl` and tells the pusher that forwarding
  and deploying are the human's. It cannot fail a push.
- The human reads through group `git` (the kit adds the user; `core.sharedRepository=group`).
- `git-hub status` — per repo/branch: hub head vs last forwarded. Local state only
  (`~/.local/state/git-hub/`), no network.
- `git-hub forward <name> [branch]` — pushes hub branches to the GitHub upstream as
  the human (their key — the YubiKey on a workstation). Never forces; GitHub refuses
  a non-fast-forward and the human merges by hand.
- `git-hub stage <name>` — fast-forwards the human's working clone
  (`$GIT_HOME/<path>`) from the hub, refusing a dirty tree or a diverged branch, then
  prints the `git_hub_deploy` command. **It never deploys.**

## Worker side (`03-headless` §8)

key → alias block → for each `git_hub_repos` clone: `origin` → `git-hub:<name>.git`,
the old GitHub URL kept as remote `github` (fetch still works with a read-only PAT)
→ probe with `git ls-remote origin`. The kit never pushes; seeding the hub is the
first `git push origin <branch>` from the worker, named in the handoff.
